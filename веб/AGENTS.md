# Vernatun Content Factory — правила разработки

Применяются вместе с корневым `../AGENTS.md`. Этот файл — основная инструкция Codex для продукта в этой папке.

## Контекст и источники правды

1. `../STATE.md` — состояние всего репозитория и текущая передача работы.
2. `DEV_PLAN.md` — активный backlog продукта; не начинай отложенные спринты до закрытия зависимостей.
3. `docs/AUDIT_FUNCTIONALITY.md` и `docs/AUDIT_ARCHITECTURE_STACK.md` — что фактически работает и как устроен код.
4. `ARCHITECTURE.md` — архитектурные принципы; aspirational-разделы перепроверь по коду и аудитам.
5. `memory/waves/`, `memory/tickets/`, `memory/trainer/` — решения и критерии предыдущей работы. Читай только относящиеся к текущему изменению.
6. `brand/`, `workers/` и `knowledge/` — правила и данные контентного продукта. Для визуального результата соблюдай активный brandbook.

Если документы противоречат друг другу, сначала проверь свежесть, код и историю git; опиши конфликт и следуй самому свежему подтверждённому решению.

## Приоритеты продукта

- Цель — рабочий контент-завод для Вернатуна; MVP и текущий спринт важнее отложенных модулей.
- Сохраняй принятый dark-luxury UI shell и текущие пользовательские сценарии. Новые экраны и редизайн не добавляй без продуктовой необходимости.
- Контент-пайплайн и инженерная команда — разные контуры. `workers/` производит контент; `plugins/`, `lib/`, API и UI реализуют продукт.
- У каждого агента должен быть узкий вход, явный контракт выхода и понятная передача следующему шагу. Не объединяй Scout, Analyst, Trainer, Разборщик и release-агентов в одну размытую роль.
- Не подменяй реальный интеграционный результат mock-успехом. Явно помечай mock/stub, если он предусмотрен текущим планом.
- Не обходи HITL: контент может стать черновиком или попасть в расписание только согласно текущим правилам; реальная отправка требует явного одобрения.

## Как вести инженерную задачу

- Маленькое изменение: проверь ближайший skill/rule, внеси минимальную связанную правку и сообщи результат.
- Задача с несколькими подсистемами: сначала очерти scope, зависимости и критерии приёмки; затем работай по ролям из `.agents/skills/content-factory-development/SKILL.md`.
- Изменение API/БД: проверь callers, schema, миграционный порядок и сохранность существующих данных.
- Изменение UI: проверь desktop/mobile сценарии и активные дизайн-токены, если пользователь запросил такую проверку.
- Изменение worker/prompt: сверь JSON-контракт, ограничения источников контекста, brand lock, передачу в HITL и product memory.
- Меняй только нужный скоуп. Не проводи массовую чистку legacy-документов и не синхронизируй зеркала механически без продуктовой причины.

## Цикл Клиент ↔ Оркестратор

Следуй `docs/CLIENT_ORCHESTRATOR_CYCLE.md` как основному рабочему порядку:

1. **Оркестратор:** уточняет scope, находит активный пункт DEV_PLAN и фиксирует критерии готовности. Для крупной/многочастной задачи сначала формирует план и цепочку ролей.
2. **Исполнение:** профильные роли последовательно закрывают работу. Тестер и фикс-этап применяются к коду в пределах запрошенной проверки; не заявляй проверку, которой не было.
3. **Клиент:** сверяет результат с критериями и, для пользовательского UI, проверяет живой сценарий через браузер. Конкретные дефекты оформляются как `C-*`, затем возвращаются Оркестратору.
4. **Повтор:** Оркестратор закрывает замечания с доказательством/guard, Клиент проводит повторную приёмку. Цикл заканчивается только когда нет открытых замечаний и реально выполнены применимые проверки.

В этой среде используй роли явно как части рабочего процесса, но не приписывай отдельному человеку/агенту действия, которых не было. Для чисто документальных правок Клиент может проверить содержание и ссылки без запуска приложения. Для UI без доступного localhost/live browser честно оставь приёмку незавершённой. Не требуй обязательного блока с вымышленными агентами; в отчёте дай два коротких раздела: «Приёмка Клиента» и «Работа Оркестратора».

## Роли и скиллы

- Codex может применять субагентов для независимых задач, когда это ускоряет работу и не создаёт пересечений по файлам. Изменения с общими файлами выполняй последовательно.
- Роли с подробными инструкциями перечислены в `.claude/registry/agents.md`; их актуальные для задачи правила находятся в `.claude/rules/`, дополнительные инженерные рецепты — в `.claude/skills/`.
- `.cursor/` и `.claude/` содержат исторические платформенные адаптации. Не считай оба дерева независимыми источниками истины и не копируй правки между ними без необходимости.
- Читая legacy rule/skill, переноси только предметные знания и продуктовые инварианты. Инструкции про Claude/Cursor-инструменты, обязательные роль-маркеры, обязательного псевдо-клиента, искусственный лимит тикетов и обязательные wave-артефакты для Codex не действуют; этот файл и запрос владельца имеют приоритет.
- Операционные инструкции микроагентов в `workers/<role>/SKILL.md` — часть поведения продукта. Не переписывай их при обычной разработке интерфейса или backend.
- Никогда не сообщай владельцу, что отдельная роль или проверка выполнялась, если она фактически не выполнялась.

## Завершение

Сообщи кратко: изменённые части, выполненные проверки (или что тесты не запускались), и оставшиеся блокеры. Не создавай commit, не отправляй push и не выкатывай production без прямого поручения.
