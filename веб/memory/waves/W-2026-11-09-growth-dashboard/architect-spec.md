## Scope и решение

Улучшить существующий `/marketing` как рабочую поверхность директора. Не создавать отдельный Site, второй analytics-продукт или ещё одну автономную HTML-доску. Сохранить текущие чат, проекты и их storage без миграций/перезаписи. Данные из mock аналитики видео не использовать как lifecycle клуба.

Новый `GrowthMarketingWorkspace` содержит вкладки:

1. **Жизненный цикл** — карта стадий, известные/неизвестные KPI, выбор стадии и конкретный playbook: продукт, аудитория/JTBD, нужный контент, действие, метрика, источник и следующий шаг.
2. **Контент и тесты** — карта тем по стадии и продукту; сначала сильная атмосфера/социальная ценность для холодной аудитории, затем FAQ и «можно прийти одному» для тёплой. Визуально отдельны назначение/гипотеза и реально измеренный эффект.
3. **Рынок** — демографическая база/источник/год, SAM неизвестно либо явно сценарий с изменяемыми допущениями; ёмкостный SOM отдельно от спроса. Сегменты по задаче, конкурентные альтернативы и проверяемое отличие.
4. **Чат директора** — существующий `MarketingDirectorClient`. Не менять prompt/API в целях UI; AI Bridge отдельно укрепляет действующий system prompt в прежнем месте.

Воронка — не декоративные выдуманные проценты. Пока измерения не подключены, одинаковые stage tiles или схема с `Нет замера`, отдельная легенда «факт / оценка владельца / сценарий / неизвестно». Не рисовать taper как фактические потери по нулевой базе.

## Структура lifecycle и события

`StageId = attraction | interest | registration | attendance | return | membership | advocacy | reactivation`.

| Стадия | Событие / сущность | Переход и ограничение |
|---|---|---|
| attraction | Дедуплицированный релевантный охват кампании | Не сумма подписчиков TG+IG, не население города |
| interest | Уникальный целевой переход/содержательное проявление интереса | Только та же кампания/период/правила dedup |
| registration | Уникальная первая регистрация | Не все заявки на шесть встреч суммарно |
| attendance | Реально пришедший впервые | Сопоставимый поднабор регистраций |
| return | Первый гость повторно пришёл за 30 дней | Деноминатор только созревшая когорта; при неизвестной зрелости процент запрещён |
| membership | Купленная/действующая подписка | Это будущий продукт, нулевой/неизвестный paid count нельзя трактовать как измеренный отказ; не обязательно поднабор return |
| advocacy | Повторный гость реально порекомендовал/привёл нового | Боковая ветка от повторного опыта, не обязательная ступень после подписки |
| reactivation | Вернулся из заранее определённой неактивной когорты | Боковая ветка; нужен собственный eligibleDormant denominator, не предыдущая stage count |

Возвращение, платное членство, рекомендации и реактивация не образуют механически убывающую линейку. UI может показывать последовательность lifecycle, но не вычислять «membership / return» или «reactivation / advocates» по соседству.

## Минимальный контракт pure data layer

Файлы: `lib/marketing/growth-model.ts` (типизация, validation, conversion, scenarios) и `growth-content.ts` (каталог стадий, кампаний, сегментов и действий; источники и даты).

Публичный API между Backend и Frontend согласуется сообщением до импорта; базовая форма:

```ts
type EvidenceKind = 'measured' | 'owner_estimate' | 'scenario' | 'unknown';
type GrowthSnapshot = {
  version: 1;
  cohortId: string;
  periodStart: string; // YYYY-MM-DD
  periodEnd: string;
  source: string;
  observedAt: string;
  evidenceKind: EvidenceKind;
  returnWindowDays: number;
  cohortMature: boolean;
  counts: Record<StageId, number | null>;
  eligibleDormant: number | null;
};
```

Метрика может дополнительно хранить единицу `people`, собственный source/date/coverage, если это нужно реализации. Не превращать снятые ранее 400 TG, 800 IG, 200 в чате, 20–30 активных, 10–12 максимум гостей в counts этой когорты. Эти вводные — отдельная baseline панель `owner_estimate` с датой, оговоркой о пересечении и неизвестном периоде активности.

Экспортировать `STAGES`, `EMPTY_SNAPSHOT`, `parseGrowthSnapshot(input: unknown)`, функцию `conversionRate(...)` (либо согласованное эквивалентное имя) и чистый scenario evaluator. Парсер возвращает discriminated result `ok / errors`; не бросает исключение наружу UI. UI не должен сам считать формулы/валидировать поля поверх другого контракта.

### Инварианты данных

- `null` — нет замера, `0` — измерено ноль; не применять `|| 0`.
- Counts — конечные неотрицательные целые числа. Периоды/наблюдение валидны и упорядочены, source/cohort не пустые.
- Пропущенные/несовместимые поля не чинить молча. При некорректном импорте прежний snapshot сохраняется. Использовать allowlist полей; посторонние поля/массивы людей/PII не принимать и не сохранять.
- Последовательные первые переходы могут использовать один dedup cohort: attraction → interest → registration → attendance. Если counts нарушают subset, ошибка качества, процент не выводить.
- Возврат: запрещён процент до maturity; `returned <= attended`. `cohortMature=true` допустим только если observedAt календарно не раньше periodEnd + returnWindowDays; признание зрелости не принимать только на слово boolean. Если отдельно поддержаны eligibleFirstAttendees — returned сравнивается с ним, не с неготовой когортой.
- Membership рассчитывается относительно явно допустимого базиса attendance; advocacy — относительно return как ветка повторного опыта, а не подписки. Не делить автоматически на предыдущую карточку. Counts не должны превышать declared base в модели одного cohort.
- Reactivation только относительно `eligibleDormant`; без него процент неизвестен. Это независимая ветка, её нельзя суммировать с первыми гостями без dedup.
- Denominator `null`/0, числитель `null`, разные периоды/единицы/когорты, scenario vs measured или неготовое окно → `value: null` с короткой понятной причиной.
- Фактические коэффициенты показывать только для `measured` совместимого snapshot. Owner estimates не маскировать под точную конверсию; scenario отдельно с явной маркировкой.

## Хранение и импорт

Первый релиз не создаёт серверную БД/API или миграции ради пустых данных. Допустим browser-local ввод/импорт только агрегированного JSON в key `cf.vernatun.growth.v1`, с полным schema validation, лимитом размера и явным текстом «сохранено на этом устройстве, без синхронизации». Не читать/собирать имена, телефоны, участнические массивы и секреты. Экспорт JSON — резервная переносимая копия; не утверждать, что это production analytics integration.

Default snapshot — все lifecycle counts `null`. Демо, если потребуется тестеру, не включено по умолчанию и не сохраняется как факт. В этой волне предпочтителен template без demo numbers.

## Маркетинговый слой

AI Bridge сохраняет узкий playbook и ссылки в ролях/реальном runtime prompt: STP/JTBD → выбор альтернативы → доказуемое отличие → cold attraction → activation → retention → monetization → referral/reactivation. Для каждого тезиса: факт/вывод/гипотеза/unknown, источник/год/география/единица, downside/контрсигнал, тест/время/лимит.

Маркетинговый исследователь пишет только `projects/vernatun/brand/growth-market-evidence-20261109.md`. Демографические census counts — исторический широкий ориентир, не реальные потенциальные покупатели 2026. Численный SAM только при наличии источников фильтров, иначе сценарная арифметика. SOM ограничен местами, частотой и ресурсом, но не доказанным спросом. Не устранять пробел рынка красивым числом.

## UI и mobile

Использовать существующие Dark Luxury токены и `--font-ui` Century Gothic. Reuse существующих UI примитивов. 21st только если реально доступен; отсутствие инструмента не блокирует существующий брендовый fallback. Обязательны русские короткие названия, видимый focus, native buttons/selects, semantic tablist/panels, reduced-motion. Никакого бесконечного pulse, фальшивой running telemetry или «победа 94%».

Текущий AppShell резервирует sidebar width на всех размерах. Разрешена минимальная route-scoped поправка только для `/marketing`: на <=767px sidebar скрыт/компактный nav предоставлен в текущем shell, content padding-left=0, header/table/cards не обрезаны. Не удалять desktop navigation, resize/persistence и не менять другие routes. Если mobile chat rail имеет min-width, ограничить/сворачивать только в этой новой workspace оболочке; не удалять проекты и не перезаписывать storage.

## Три тикета и приёмка

1. **C-GROWTH-01, P0:** data contract, unknown/zero semantics, safe import, conversions/scenarios; unit tests реальных границ, без тестов зеркалящих текст компонента.
2. **C-GROWTH-02, P1:** встроенный dashboard lifecycle + контентная карта + рынок + сохранённый чат; desktop/mobile/keyboard/live scenario.
3. **C-GROWTH-03, P1:** метод агентов/действующий prompt + attraction-first корректировка и evidence market.

Готово для передачи владельцу: код собирается/типизируется в пределах проекта (унаследованные ошибки указать отдельно), содержательные guards проходят, локальный маршрут отвечает, фильтры/стадии/импорт/ошибки/периоды/пустоты проверены, чат/проекты доступны, 1440 и 360/390 не обрезаются. Независимый Клиент/Tester реально проверяет UI, если браузер доступен. При внешнем browser блокере не объявлять финальную UI-приёмку завершённой, вернуть конкретное ограничение.

Production deploy, публикация, платные API, массовая рассылка и новый биллинг в scope не входят. Пользовательский запрос делает новую поверхность внутри `/marketing` продуктово оправданным исключением shell-freeze, не разрешением редизайна всей фабрики.
