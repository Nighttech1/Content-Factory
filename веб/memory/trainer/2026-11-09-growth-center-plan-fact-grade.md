## Обязательные контракты до кода

### 1. Стадии: новая семантика, не простое переименование

- `awareness`: уникальные люди, узнавшие о клубе в заданном измерительном контексте. Impressions/views/followers — отдельные proxy-метрики; их нельзя подставить в people одной когорты.
- `desire`: наблюдаемое намерение/интерес с явным событием (например, переход к условиям/осмысленная заявка интереса), а не субъективно угаданное «захотел». Назвать инструмент/операционное определение.
- Остальные события: регистрация, первый фактический приход, повтор в окне, купленное/действующее членство — с точными определениями и периодами.
- Referral и reactivation имеют собственные базы/события: приглашение друга не равно фактически пришедшему по рекомендации; реактивация считается от заранее заданной dormant-когорты.
- Изменение `attraction/interest` на `awareness/desire` меняет смысл старых цифр. Нельзя молча считать старое `attraction=захотеть` новой узнаваемостью. Версия схемы, явное legacy mapping/отклонение либо сохранение прежнего снимка с надписью «требует классификации».
- Основная отрисовка может быть линейной по запросу владельца, но реальные формулы membership/referral не обязаны брать предыдущий прямоугольник: знаменатель определяется событием и источником. Оплата не требует обязательного повторного визита, если продукт допускает покупку раньше. Не рисовать ложную обязательную причинность.

### 2. Глобальный План / Факт

| Слой | План | Факт |
|---|---|---|
| Стадия | Target, период, единица, владелец цели, основание/допущения, дата фиксации | Измеренный count/rate с источником, датой наблюдения, периодом/когортой и методикой |
| Контент | Конкретный V-ID из канонического месячного плана, тема, формат, канал, запланированный слот, стадия и CTA | Только доказанная публикация: V-ID, URL, фактическая дата/время и канал; статус `published` без ссылки/даты недостаточен |
| Посещаемость | Цель события/недели; capacity как ограничение | Пришедшие на конкретное событие и агрегаты периода, отдельно уникальные люди и посещения |
| График | Пунктир/подпись «цель», не «прогноз» | Наблюдения, provenance; отсутствующее значение — разрыв/пустота |

Переключение глобальное: карточки стадий, их детали, контент и соответствующий chart отражают выбранный режим. Нельзя поменять только бейдж над прежними значениями. Цели не становятся «фактом» от истечения даты. `approved`, `scheduled`, `на апруве` не published. Производная/кросспост имеет отдельное доказательство размещения и не увеличивает число новых оригиналов.

### 3. Shared / durable / protected

- Browser `localStorage` допустим для локального выбора вкладки, но не как основное общее хранилище метрик/публикаций/плана.
- Серверный storage должен быть реально долговременным: существующая БД либо явно заданный persistent path/volume **вне пересоздаваемого кода релиза**. Нельзя считать `cwd/data` автоматически сохранным при deploy. Если путь не настроен — endpoint возвращает storage-not-configured, а не пишет в эфемерную память с `ok:true`.
- Изоляция по проекту/workspace; не смешивать Vernatun с Fingrad. В этой задаче достаточно обезличенных агрегатов, не списка телефонов/персональных профилей.
- Запись только через аутентифицированный/авторизованный executor, серверная строгая валидация, allowlist полей, ограничение размера, защищённая конфигурация credentials. Не строить auth из browser role/localStorage. В текущем `/api/marketing/chat` видимого auth guard нет — мутации не добавлять туда незащищённым побочным эффектом.
- Revision / `expectedVersion` и conflict 409 предотвращают lost update. `actionId` предотвращает повторную запись одной операции. Atomic transaction либо temp+rename+locking для single-writer файла; частично записанный JSON недопустим. Многопроцессность/PM2 должна соответствовать выбранному storage.
- Audit: кто/чем/когда внёс, источник, до/после или ref на before, причина/поручение, версия. Идемпотентность не должна скрывать конфликт изменившейся операции.
- Chat update означает: владелец поручил → инструмент/executor сформировал и валидировал изменение → protected server mutation → readback/version receipt. Текст «обновила» из LLM без записи не обновление. Сам LLM не пишет в БД и не получает секрет.
- Ошибка auth/storage/validation не затирает старое состояние. Нельзя при ошибке чтения тихо заменить persistent store пустым snapshot и записать его обратно.

### 4. Provenance и графики

- Для каждой точки нужны scope, unit, period/event/cohort, value nullable, kind, sourceRef, observedAt; targetAt и recordedAt отличаются от даты факта.
- Transition chart допускает либо когортную конверсию с известной совместимой базой и завершённым окном, либо честные counts переходных событий за период. Не делить независимые недельные totals как одну когорту.
- Не заполнять пустые недели нулями, интерполяцией, «демо» или последним известным значением без явного режима/методики. `null` — gap; измеренный 0 — точка нуля.
- Не строить событие перехода простым `snapshot[t]-snapshot[t−1]`, если snapshots накопительные/исправляемые/разные когорты. Исправление старых данных не является отрицательным новым клиентом.
- Attendance chart отдельно от funnel: дата события, фактические посещения, вместимость/план при наличии. Несколько визитов одного человека — несколько посещений, не новых людей.
- Дубли опубликованных URL/внешних IDs, событий и идемпотентных updates не увеличивают факт. Таймзона отображения Europe/Moscow, timestamp хранить однозначно.
- Сравнение plan/fact имеет смысл только при одном периоде/единице; невозможная/нулевая база → нет процента, не Infinity/NaN/100%.

## Рекомендуемая цепочка и минимальные навыки

1. Архитектор: scope, schema v2, перенос/сохранение legacy v1, источник durable storage, topology стадий, auth/update contract и deployment persistence до кода.
2. Backend: data model/store/API + chart aggregation, safe migrations/zero-data-loss; без разрушения старого хранилища и без новых платных сервисов.
3. AI Bridge: безопасный chat-handoff к executor, роли источников/targets/fact, ссылки на V-ID и публикации. Runtime guard на то, что инструкция реально попала в prompt/вывод инструмента, не просто markdown.
4. Frontend: отдельный route/раздел «Центр роста» в текущем shell, крупная интерактивная воронка, единый Plan/Fact, stage detail с профилем/контентом/тактиками и реальные временные charts.
5. Tester/Fixer: данные/безопасность/типы/build/SSR/live UI с независимой проверкой.
6. Деплоер: существующий production path, бэкап/проверка persistence, deployment только после закрытия QA, health/readback после релиза.

Маркетинговые навыки предыдущей волны уже усилены; эта волна требует не ещё одной общей лекции, а конкретного определения событий и доказательств исполнения. Учить агента: target ≠ scenario ≠ measured; publish fact ≠ одобрение; chat assertion ≠ durable mutation.

## Обязательные исполняемые guards

- Missing/invalid authorization → 401/403, old store unchanged; legacy unprotected chat не может вызвать write.
- Valid protected update → persisted revision, readback; stale revision → 409; repeated actionId → no duplicate; malformed/extra PII fields rejected.
- Process restart/read сохраняет данные; deploy implementation не перезаписывает persistent path. Если проверено только локально — не объявлять production durability.
- Legacy stage snapshot не переинтерпретирован молча как awareness/desire.
- Плановый V-ID доступен в Plan; в Fact отсутствует до URL+publishedAt+канала. Draft/approved/scheduled не считаются публикацией.
- Null/0/negative/fraction/NaN, несовместимые единицы и periods; известные ancestry через null; зрелость return; независимые referral/reactivation bases.
- Time charts: пустая неделя gap; измеренный ноль сохранён; исправление snapshot не новый переход; повтор URL/события dedup; attendance визиты != unique people.
- План/Факт переключается на всех относящихся блоках, переходы и attendance charts доступны, источники видны.
