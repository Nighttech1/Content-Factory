# Цикл «Клиент ↔ Оркестратор»

Рабочий порядок для разработки Vernatun Content Factory. Главные инструкции — корневой `AGENTS.md` и `веб/AGENTS.md`; этот файл задаёт цикл приёмки. Сохранившиеся `.claude/` и `.cursor/` содержат платформенные и исторические материалы, применяй из них предметные знания, а не специфичные для старой среды требования.

## Роли

- **Оркестратор** принимает запрос владельца, определяет scope и критерии, направляет работу по нужным инженерным ролям, следит за фиксацией замечаний и сообщает состояние.
- **Клиент** независимо сверяет результат с критериями, проверяет нужный пользовательский сценарий и выдаёт конкретные замечания `C-*` либо подтверждает приёмку.
- Роли описывают этапы проверки. Не утверждай, что отдельный агент выполнял работу, если он не был вызван; не выдумывай вердикты, скриншоты или проверки.

## Цикл

### A. Клиентская проверка исходного результата

1. Сверь задачу с `DEV_PLAN.md`, её критериями и актуальным состоянием кода.
2. Для UI проверь живой сценарий в браузере на localhost, включая desktop и mobile, если это применимо и окружение доступно.
3. Запиши каждый воспроизводимый дефект как `C-*` с ожидаемым и фактическим результатом и шагами воспроизведения. Для документационных задач проверь содержание, ссылки и согласованность инструкций.
4. Передай список замечаний Оркестратору. Если дефектов нет, зафиксируй, что проверено и каким способом.

Если localhost или браузер недоступны, не объявляй UI приёмку завершённой: перечисли непроверенные критерии.

### B. Волна Оркестратора

1. Для крупной задачи зафиксируй scope, зависимости и критерии завершения; Тренера подключай, если нужно изменить или диагностировать навыки команды.
2. По необходимости создай `memory/waves/W-*.md` с `before_sha`, а для многочастной задачи — план и цепочку ролей до начала кода.
3. Закрой замечания `C-*` профильными ролями. Не параллель изменения общих файлов.
4. Выполни проверки, соответствующие изменению и запросу владельца. Для кода используй существующие тесты/guards; для документации проверь согласованность и ссылки. Не ослабляй проверки ради зелёного результата.
5. Зафиксируй доказательство закрытия каждого замечания в guard или в тикете. Не закрывай тикет без доказательства.

По умолчанию одна волна берёт не более трёх тикетов, если пользователь не попросил закрыть весь объём. Локальная приёмка не означает разрешение production deploy; выкладка требует прямого поручения.

### C. Повторная приёмка Клиентом

После волны Клиент проверяет закрытые замечания и регрессии. Если остались дефекты, добавляет или переоткрывает `C-*` и возвращает задачу Оркестратору. Повторяй цикл до закрытия применимых замечаний и проверок.

Для UI приёмка завершается только при наличии живого прогона применимых сценариев. Для задач без UI — после проверки артефакта по критериям задачи.

## Отчёт о завершении

В финале кратко раздели:

- **Приёмка Клиента:** вердикт, проверенные сценарии/артефакты, открытые `C-*` и ограничения.
- **Оркестратор:** что изменено, какие guards/проверки выполнены, что осталось.

Слово **«согласовано»** используй только если нет открытых применимых замечаний и все требуемые гейты реально пройдены. Для незавершённой UI-приёмки укажи, что цикл остаётся открытым.
