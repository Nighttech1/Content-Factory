# Контент-фабрика — правила работы Codex

Эти правила относятся ко всему монорепозиторию. Для задач в `веб/` сначала прочитай `веб/AGENTS.md`.

## Что здесь разрабатываем

- `веб/` — действующий продукт Vernatun Content Factory. План разработки и текущие приоритеты находятся в `веб/DEV_PLAN.md`, фактическое состояние кода — в `веб/docs/AUDIT_FUNCTIONALITY.md` и `веб/docs/AUDIT_ARCHITECTURE_STACK.md`.
- `projects/vernatun/` и `projects/fingrad/` — материалы контентных проектов и их бренды. Не смешивай данные между проектами; перед контентной задачей проверь `ACTIVE_PROJECT`.
- `shared/`, корневые `PLAN.md` и `ARCHITECTURE.md` описывают исходную концепцию контент-процесса. Для разработки приложения они уступают актуальным документам из `веб/`.
- Для контентной стратегии и планирования проекта Вернатун используй `projects/vernatun/AGENTS.md`, профиль `.codex/agents/content_director.toml` и узкие навыки из `.agents/skills/vernatun-*/`. Не смешивай этот контур с разработкой приложения и инструкциями продуктовых workers.

## Рабочий порядок

1. Прочитай `STATE.md`, относящийся к задаче план и ближайшие документы продукта. Не перечитывай всю базу знаний без необходимости.
2. Проверь `git status` и последние изменения до правок. Не перезаписывай незакоммиченные изменения пользователя.
3. Для заметной продуктовой работы зафиксируй короткий scope, затронутые файлы и критерий готовности. Для небольших правок переходи прямо к делу.
4. Используй существующие роли и скиллы по задаче. Основная карта находится в `веб/.agents/skills/content-factory-development/SKILL.md`; исторические инструкции ролей — в `веб/.claude/rules/` и инженерные скиллы — в `веб/.claude/skills/`.
5. Сохраняй принятые решения и инварианты продукта. Если код расходится с документацией, сначала проверь аудит и историю изменений; не выдавай планируемое поведение за реализованное.
6. В конце кратко сообщи, что изменено, что проверено и какие ограничения остались. Не утверждай, что проверки или публикация выполнены, если этого не было.

## Цикл «Клиент ↔ Оркестратор»

Для разработки веб-продукта следуй `веб/docs/CLIENT_ORCHESTRATOR_CYCLE.md` и уточнениям в `веб/AGENTS.md`: Оркестратор принимает запрос и ведёт работу; Клиент независимо сверяет результат с критериями, выдаёт замечания `C-*` и только затем фиксирует приёмку.

Это роли проверки, а не повод изображать несуществующих участников. Если для независимой приёмки используется отдельный агент, явно сообщай только реально выполненную проверку. При live UI-задаче принимай результат по живому пользовательскому сценарию в браузере; если приложение недоступно, отмечай приёмку как незавершённую. Для документационных изменений проверяй документы и ссылки по их критериям без притворного UI-прогона.

Существенную волну веди через scope/критерии → план Архитектора → выполнение профильных ролей → нужные проверки и фиксы → приёмка Клиента. Замечания закрывай с доказательством/guard. Лимит волны — до 3 тикетов по умолчанию, если пользователь не просит пройти весь объём. В финале разделяй результат приёмки Клиента и сводку Оркестратора; не заявляй «согласовано», если есть открытые замечания или незавершённые обязательные проверки.

## Правила изменений

- Не удаляй и не сбрасывай пользовательские данные, Postgres/Redis volumes, медиа или резервные копии. Не выполняй `prisma migrate reset`, `DROP`, `TRUNCATE` и destructive restore на общих окружениях.
- Секреты хранятся только в переменных окружения и локальных `.env`; не добавляй их в Git, логи, memory или артефакты.
- Публикация контента требует прохождения продуктового HITL и явного одобрения владельца. Одобрение черновика не означает разрешение автоматически публиковать его.
- Сохраняй пользовательские данные и существующие API-контракты. Для схем БД предпочитай additive-миграции и совместимые этапы перехода.
- Тяжёлые медиа не коммить: в репозитории хранятся ссылки и манифесты.
- Не добавляй тесты и не запускай широкие наборы без необходимости. В рамках запрошенного цикла Клиент ↔ Оркестратор выполняй подходящие существующие проверки кода; для чисто документальных правок ограничься проверкой текста/ссылок. Явно укажи результат.
- Не делай `git commit`, `push`, merge или production deploy без отдельного запроса. Рабочие изменения оставляй доступными для просмотра в текущей ветке.

## Общение

Общайся с владельцем напрямую, по-русски, ясно и без искусственных отчётов от имени вымышленных агентов. Уточнения задавай только тогда, когда без ответа нельзя безопасно выбрать направление; иначе продолжай с прозрачным разумным предположением.
