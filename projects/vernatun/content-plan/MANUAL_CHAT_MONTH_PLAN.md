# План разработки ручной контент-фабрики

> Цель: за один месяц доказать на реальных задачах, что роли и пайплайны стабильно
> производят принятый контент без автономного запуска чатов. Отметка `[x]` означает
> проверенный результат, а не только созданный документ.

### Результат дня

## Результат первой волны

После закрытия первой волны система должна позволять директору создать задание,
владельцу вручную передать его одному отделу, получить пакет после редактора и
увидеть тот же ID в Git и, когда веб доступен, в веб-интерфейсе. Автоматический
запуск чатов, публикация и платные API в эту волну не входят.

## 0. Решения и доступы владельца

- [ ] Выбрать один формат для первого полного прогона: карусель, рилс или статья.
- [ ] Назвать 1–3 реальных ID из утверждённого плана, которые можно использовать как пилот.
- [ ] Подтвердить, где лежат референсы этого формата: путь в репозитории, папка Drive или ссылки.
- [ ] Открыть отдельные чаты ролей, подключив к каждому один и тот же репозиторий `Content-Factory`.
- [ ] Вставить стартовый текст из раздела «Новый чат» в каждый чат и указать его роль.
- [ ] Сообщить только статус веб-витрины: доступна / VPS недоступен. Не передавать ключи в чат.
- [ ] Когда потребуется перенести новые документы в другие чаты из GitHub, явно разрешить commit + push. До этого работа остаётся в текущей рабочей копии.

**Гейт владельца для старта волны:** выбран формат, есть хотя бы один ID и понятный источник референсов.

## 1. Единый контракт задания

- [x] Зафиксирован формат ID и состояния задачи в `content-plan/README.md`.
- [x] Зафиксирован ручной транспорт и границы ролей в `MANUAL_CHAT_ARCHITECTURE.md`.
- [ ] Проверить на выбранном ID, что в плане есть цель, формат, канал, CTA, дедлайн, адресат, входные материалы и критерии приёмки.
- [ ] Дописать недостающие поля без изменения утверждённой стратегии.

**Критерий:** начальник отдела может начать работу, не спрашивая историю разговора директора.

## 2. Настройка чатов-ролей

- [ ] Контент-директор прочитал бренд, план, свой профиль и память; создал/уточнил задание.
- [ ] Скаут прочитал свой профиль и умеет возвращать отчёт с источниками, а не свободные идеи без проверки.
- [ ] Лид выбранного отдела прочитал только собственные правила, память и профильный пайплайн.
- [ ] Редактор читает бриф, критерии и черновик, выдаёт однозначный ✅/❌ с замечаниями.
- [ ] В каждом чате проверено наличие нужного навыка, плагина или MCP непосредственно перед использованием; отсутствие фиксируется как блокер, а не имитируется.

**Критерий:** роли не дублируют работу и не пишут в чужую память.

## 3. Пилотный цикл контента

- [ ] Директор создаёт или уточняет бриф пилотного ID и ставит статус `назначено`.
- [ ] При необходимости скаут готовит краткий отчёт с источниками и ссылками; директор решает, что из него входит в бриф.
- [ ] Владелец передаёт ID лидеру отдела; лидер подтверждает входные данные и ставит `в работе`.
- [ ] Отдел создаёт пакет черновика по своему пайплайну и фиксирует ссылки на ассеты.
- [ ] Владелец передаёт ID редактору; редактор выдаёт ✅ либо список исправлений.
- [ ] При ❌ отдел исправляет только указанные замечания и возвращает новую версию на редактуру.
- [ ] Владелец получает пакет, даёт апрув или правки. До апрува статус остаётся `на апрув`.
- [ ] После апрува фиксируются статус `одобрено`, ссылка на готовый материал и решение владельца о ручной публикации.
- [ ] Если веб доступен, проверить отображение ID и результата; если нет — зафиксировать это как технический блокер, не как провал контента.

**Критерий:** один ID проходит весь путь без потери брифа, источников, версии и редакторского решения.

## 4. Еженедельное улучшение без хаоса

- [ ] Директор сверяет план с результатами скаута и аналитика, но не переписывает прошлые задания задним числом.
- [ ] Каждая роль добавляет в свою память только подтверждённый урок с датой и правилом действия.
- [ ] Новый скилл, плагин или MCP сначала проверяется на одном пилотном задании.
- [ ] После проверки правило, назначение инструмента и ограничение фиксируются в профиле нужной роли; секреты не записываются в Git.
- [ ] Раз в неделю владелец отмечает: продолжить ручной режим / автоматизировать конкретный стабильный переход / удалить неподтверждённое правило.

**Критерий:** улучшения уменьшают число правок редактора, а не создают новые параллельные правила.

## Минимальный пакет на редактуру

```text
ID:
Версия брифа:
Формат и канал:
Ссылка на исходник / готовый материал:
Подпись и CTA:
Использованные референсы:
Самопроверка по критериям:
Что требует решения владельца:
```

## Метрики успеха месяца

- каждое задание можно восстановить по ID без чтения истории чужих чатов;
- у каждой единицы есть бриф, автор этапа, редакторский вердикт и статус;
- минимум один полный цикл проходит для каждого используемого формата;
- повторяющиеся замечания редактора превращаются в правила или уроки памяти;
- владелец видит план и состояние работ в Git и веб-интерфейсе;
- ни один материал не опубликован без явного апрува владельца.

## Решение по итогам месяца

Автоматизацию обсуждаем только после просмотра журналов заданий и памяти ролей. Автоматизируем сначала один доказанно стабильный переход, например: напоминание директору о плановом задании или запуск скаута по расписанию. Нестабильные этапы остаются ручными.

## Что команда сделает за одну волну после вашего гейта

После выполнения раздела 0 команда может за одну ограниченную волну:

- проверить бриф и привести выбранный ID к единому контракту;
- сверить и укрепить инструкции только выбранных ролей;
- подготовить шаблон пакета передачи и журнал редакторских замечаний;
- провести один полный ручной цикл до статуса `на апрув`;
- проверить веб-витрину, только если она фактически доступна;
- оформить подтверждённые уроки и отчёт о готовности следующего формата.

В эту волну не входят восстановление VPS, выпуск в соцсети, подключение платных API,
автоматический запуск чатов или перенос всей фабрики на новую платформу. Для них нужны
отдельные решения владельца и отдельные проверяемые волны.

Перед началом назови прочитанные входные данные и критерии приёмки.
После работы обнови статус, подготовь пакет передачи и запиши только
