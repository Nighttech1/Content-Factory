Дата аудита: 16.11.2026. Это контракт для серверной команды. Получатель ещё не реализован в данной ветке.

не исходниками бота. Расшифровка не требуется для этой задачи.
Нельзя подменять рабочий бот новым только из-за отсутствия его исходников в этом Git.

## Авторизация доставки

GitHub POST на настроенный HTTPS endpoint. Путь назначает серверная команда,
например /api/integrations/articles. Заголовки:
X-Article-Timestamp (Unix seconds), X-Article-Signature (sha256=HEX),
Idempotency-Key (id:revision:content_sha256). HMAC-SHA256 вычисляется от
timestamp + "." + точные байты тела с общим секретом. Секрет только в Actions/VPS.

Получатель ограничивает размер тела, проверяет временное окно ±300 секунд,
сравнивает подпись constant-time, валидирует схему и одобрения. Принимает только
approved с наступившим publish_at и актуальным SHA. Разрешены доверенные
репозиторий/ветка и издатель. Настройка секрета не должна давать публичную
возможность загружать статьи без проверки.

## Серверный порядок

1. Под блокировкой на article id проверить revision. Старую отклонить 409.
   Та же revision с другим hash отклоняется. Повтор того же ключа возвращает
   прежний receipt без повторной записи или уведомления.
2. Рендерить текст с HTML escaping и ограниченным набором блоков. Запретить
   произвольный HTML/JS и опасные URL. Медиа не скачивать без отдельной защиты
   от запросов во внутреннюю сеть.
3. Сначала сформировать новую страницу во временном файле, затем атомарно
   заменить её. Сохранить старую версию. Не выполнять rsync --delete корня сайта.
   Сохранить существующие статьи и URL.
4. Обновить каталог /articles, canonical, Open Graph, Article/BreadcrumbList,
   sitemap и RSS. Проверить страницу по публичному URL с ожидаемым hash/revision.
   Не заменять весь sitemap только списком новых статей.
5. Синхронизировать тот же id/revision с существующим дашбордом. Проверить его
   реальный контракт /api/content/ingest до применения; пример из старой инструкции
   не доказывает совместимость blocks. Статус published ставится только после сайта.
6. Записать в устойчивую outbox событие article.published в одной транзакции
   с записью результата. Публикация на сайте должна предшествовать Telegram.
7. Worker на VPS вызывает внутренний endpoint действующего бота с HMAC,
   event_id, article id, revision, title, teaser и проверенным URL сайта.
   Если бот находится на том же VPS, допустим внутренний вызов его функции
   через очередь вместо HTTP. Это прикладной webhook, а не Telegram setWebhook.
8. Бот публикует короткий анонс и ссылку в @mosarmclub через sendMessage.
   Перед production проверить getMe и права администратора can_post_messages.
   Канал должен быть закреплён в конфигурации сервера, не браться из статьи.
9. Сохранять Telegram message_id. Обновление статьи редактирует существующий
   анонс, повторная доставка не создаёт новый. Повторы 429 учитывают retry_after.
   При таймауте после sendMessage статус uncertain и ручная сверка:
   Bot API не гарантирует exactly-once при неизвестном исходе отправки.
10. Повторно сверять сайт, дашборд и очередь по расписанию. Потеря мгновенного
    webhook не должна терять статью. Частичный успех хранится отдельно.
    Аварийное снятие публикации выполняется отдельной явной операцией.

Ответ HTTP 200 после успешного сайта, синхронизации дашборда и устойчивой записи
уведомления:
```json
{
  "id": "V-202611-ART-999",
  "revision": 1,
  "content_sha256": "<SHA256 content>",
  "url": "https://vernatunspeakclub.com/articles/example",
  "site_status": "published",
  "dashboard_status": "synced",
  "telegram_status": "queued"
}
```

queued не означает sent. Для отключённого анонса telegram_status=disabled.
Повторные вызовы не должны возвращать успешный receipt для изменённого содержимого.

- [x] Отправитель с HMAC и запретом перенаправления секрета на другой адрес.
- [ ] Найти исходники и runtime действующего Telegram-бота.
- [ ] Подтвердить реальный корень сайта, резервные копии и текущие старые URL.
- [ ] Реализовать серверный endpoint, рендер и атомарную запись.
- [ ] Подключить текущий дашборд с проверенным контрактом.
- [ ] Реализовать outbox, блокировку по id и получатель webhook в боте.
- [ ] Связать имена Secrets/Variables с сервером, не копировать значения в Git.
- [ ] Проверить в тестовом канале успешную доставку, повтор, старую revision,
      будущую дату, неподписанный POST, сбой сайта, сбой бота и unknown send outcome.
- [ ] На одной одобренной владельцем статье подтвердить публичную страницу,
      запись дашборда и один анонс со ссылкой. Только тогда включать основной канал.
