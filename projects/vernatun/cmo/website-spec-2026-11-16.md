## 1. Цель и границы

Пользователь должен выбрать подходящее событие, увидеть полные условия и записаться именно на выбранную встречу. Статьи должны помогать знакомиться с клубом и переходить к подходящему событию. Основные результаты измеряются завершёнными регистрациями и фактическими посещениями.

Владелец поручил подготовить ТЗ, вести краткую память решений в Git, получать расписание автоматически из существующей Google-таблицы и доставлять статьи из Git контент-фабрики на сайт с отображением в её дашборде.

Изменяем существующий сайт. Сохраняем домен, логотип, фирменную систему, рабочие разделы и адреса статей. Сначала используем существующий бот регистрации. Отдельная система билетов или новый личный кабинет не являются обязательными для первой версии. Пригодность бота и контракт event_id команда обязана проверить до реализации записи.

ТЗ задаёт требования, а не утверждает наличие готовых API, репозитория сайта, рабочих расписаний агентов или очереди публикаций. Проверенный репозиторий Content Factory не следует автоматически считать репозиторием публичного сайта.

Предлагаемые адреса /events/{event_id}-{slug} и параметры фильтров являются проектными требованиями. Наличие таких маршрутов сегодня не подтверждено.

Прямой переход к конкретному событию возможен только после реализации и проверки его поддержки ботом. Если deep link пока не работает, показывать честную инструкцию выбора события и не терять его название/дату.

- [ ] Провести аудит текущего бота, реестра записей и check-in.
- [ ] Передавать стабильный event_id и короткую метку источника. Формат Telegram start payload согласовать с ботом; не считать произвольную ссылку рабочей.
- [ ] Не требовать регистрацию нового аккаунта сайта перед показом условий и переходом в бот.
- [ ] Разделить registration_started, pending, confirmed, waitlisted, cancelled, attended, no_show. Оплату учитывать отдельным payment_status, не выводить её из статуса посещения.
- [ ] Уникальность записи задаётся event_id + participant_id. Повторное нажатие не создаёт дубль.
- [ ] Лимит мест и последнее свободное место проверяются атомарно в существующем реестре. Google Sheets не хранит оперативный остаток мест.
- [ ] Уведомление о подтверждении содержит событие, место, время, оплату и возможность отмены.
- [ ] Дать участнику способ повторно увидеть запись. Не делать сообщение «Вы записаны» после одного клика по кнопке.
- [ ] Посещаемость приходит из check-in. Открытие страницы, звонок в комнату и подтверждение записи не равны визиту.
- [ ] При недоступном боте объяснить проблему и показать проверенный контакт. Контакт не создаёт фиктивную регистрацию.
- [ ] Нативную форму на сайте добавлять только при необходимости, используя тот же реестр и проверку контакта. Поля: имя, один канал связи и нужные для события сведения. Никакой второй таблицы участников.

Приёмка: повтор запроса не создаёт дубль; при двух одновременных запросах на одно место подтверждается максимум один; отмена освобождает место по согласованной политике. Лист ожидания не равен подтверждённому месту.

## 6. Синхронизация расписания

Предлагаемый путь: Google Sheets → один серверный импортёр → валидированный снимок событий → сайт и представление в дашборде. Источником описаний и дат остаётся таблица; источником записей и мест остаётся регистрационная система.

Место выполнения определить на WEB-00. Если VPS может читать Sheets API, импортёр работает на сервере. Если исходящий доступ из VPS ограничен, использовать доступный внешний сборщик и доставку проверенного снимка. Не строить интеграцию вокруг предположения о доступности API.

- [ ] Читать только согласованные вкладки и диапазоны через read-only доступ. Не требовать публикации всего файла в интернет.
- [ ] Передавать credentials через существующее защищённое окружение. Не отдавать их браузеру и не писать в Git.
- [ ] Нормализовать DD.MM.YY, 20-00 и 20:00 с явной timezone. Не переносить примерное «3 часа» в ends_at без подтверждения.
- [ ] Валидировать уникальные ID, обязательные поля, конец позже начала, допустимые категории и статусы.
- [ ] Разрешать публикацию только approved/published строк согласно согласованной таблице статусов.
- [ ] Свободный текст примечания не является HTML или командой на выполнение. Извлекать только согласованные публичные поля.
- [ ] Ошибка строки не должна публиковать её частично. Сохранять её предыдущую валидную версию и помечать проблему; новая ошибочная строка не публикуется.
- [ ] При недоступном источнике сохранять последний успешный снимок и служебную дату синхронизации.
- [ ] Пустой ответ, изменение заголовков или резкое исчезновение строк не должны массово отменять события. Требовать подтверждённого статуса cancelled/archived.
- [ ] Сортировка или вставка строк не создают дубли. Импорт повторной revision идемпотентен, то есть не меняет результат.
- [ ] Доставлять снимок атомарно, с schema_version, revision, generated_at и хешем. Не допускать смешения старого календаря и новых карточек.
- [ ] Предлагаемая цель: обновление опубликованных изменений за 5 минут при исправных источнике и исполнителе. Период опроса команда выбирает после проверки квот и среды.
- [ ] Если снимок старше 15 минут, показывать служебный warning ответственному; после 30 минут согласовать публичное предупреждение об актуальности. Время является целевым требованием, не текущим SLA.
- [ ] При рассинхронизации статуса записи и описания использовать регистрационный сервис для решения о наличии мест; не подтверждать запись по кешу.
- [ ] Поддержать ручную повторную синхронизацию для уполномоченного администратора, с журналом ошибок без секретов.

Google Sheets API имеет квоты [R8]. GitHub Actions schedule может запускаться с задержкой [R9]; для гарантированного пятиминутного обновления он не должен быть единственным механизмом. Точное расписание генерации статей с таким механизмом также не обещать.

## 7. Статьи из Content Factory: один источник и две доставки

Пользователь подтвердил направление автоматизации. Подготовка статьи по расписанию и техническая доставка должны быть автоматизированы. Действующие Editor + owner approval сохраняются: текущая просьба не отменяет проверку каждого публичного материала.

Если владелец позднее утвердит пакет материалов или отдельную политику автоматического одобрения, хранить точную область и версию такого разрешения. До этого автоматическая генерация создаёт черновик; автоматическая публикация применяется только к одобренной версии после publish_at.

### Источник

Сохраняем существующий отдел:
projects/vernatun/departments/article/jobs/{ID}/.
Используем действующий месячный план и ID статьи. Не создаём новый тип агента и параллельный календарь.

В jobs лежат бриф, текст/блоки статьи, манифест ссылок на медиа и вердикт редактора. Существующий старый путь drafts может остаться входом адаптера; команда должна выбрать один канонический путь для новых работ и явное соответствие старых ID.

Медиа остаются во внешнем хранилище. Не помещать тяжёлые файлы в Git. Изображения показываются между нужными абзацами, а не одной галереей в конце.

### Контракт статьи, предлагаемый v1

| Поле | Значение |
| --- | --- |
| article_id, job_id | Стабильный ID и связь с существующим заданием. |
| schema_version, revision | Версия формата и монотонная версия статьи. |
| content_hash, source_commit | Контроль содержания и точная исходная версия Git. |
| title, slug, excerpt | Заголовок, постоянный адрес и анонс. |
| blocks | Упорядоченные heading, paragraph, list, image, quote, video. |
| category, tags, audience | Раздел, темы и сегмент; разрешённые значения проверяются. |
| author, reviewer | Честная атрибуция. Не придумывать автора или экспертную проверку. |
| sources, verified_at | Первичные ссылки и дата проверки фактов, если применимо. |

Публикационные статусы получателей хранятся отдельно: site_delivery и dashboard_delivery. Каждый содержит desired_revision, delivered_revision, status, last_attempt_at, error_code и подтверждённый URL или ID записи. Успех сайта не означает успех дашборда.

Изменение публичного текста или медиа после approval инвалидирует одобрение этой версии. Отмена материала блокирует новые попытки публикации; снятие уже опубликованной версии требует отдельного зарегистрированного действия.

### Последовательность

- [ ] Планировщик читает одобренные задания отдела статей и создаёт запуск по job_id + plan_revision. Точные дни и время генерации владелец задаёт отдельно в существующем календаре.
- [ ] Использовать существующего scriptwriter-article в поддерживаемом облачном исполнителе. Наличие Markdown-профиля или cron не означает, что LLM-агент умеет работать по расписанию.
- [ ] До выбора механизма подтвердить доступный исполнитель, подписочный/API-путь и разрешённые расходы. Не подключать новый платный API по умолчанию и не строить неподдерживаемую автоматизацию интерфейса чата.

- [ ] Редактор проверяет материал; одобрение владельца привязывается к content_hash.
- [ ] Планировщик публикации берёт только одобренные версии, у которых наступил publish_at.
- [ ] Один координатор отправляет одну revision на сайт и в существующий дашборд. Адаптер переиспользует существующий API, если он подтверждён.
- [ ] Повторная доставка по article_id + revision обновляет запись, а не создаёт вторую.
- [ ] Сайт отвечает принятым ID, revision и URL. Дашборд хранит подтверждение и состояние обоих получателей.
- [ ] При недоступном дашборде успешный сайт не публикуется заново; повторяется только доставка/подтверждение дашборда. При недоступном сайте дашборд показывает «публикация не завершена».
- [ ] Периодическая сверка сравнивает желаемую и фактическую версии; восстанавливает пропущенную доставку после потери webhook.
- [ ] Конкурирующие запуски защищаются блокировкой по article_id; старый запуск не перезаписывает более новую принятую revision.
- [ ] Ограничить количество повторов с увеличением интервала. После исчерпания оставить задачу в состоянии failed и уведомить ответственного.
- [ ] Не включать дашборд в поисковую индексацию. На нём показывать статус доставки и ссылку на публичный оригинал.
- [ ] Не копировать текст обратно из дашборда в Git без отдельного утверждённого механизма редактирования.

В ростере упоминается POST /api/content/ingest. Прямая проверка предполагаемого файла route.ts вернула 404. Команда должна найти фактический маршрут и проверить аутентификацию, контракт article/blocks и модель сохранения. Предлагаемые новые интерфейсы не объявляются существующими.

### Безопасная доставка и выпуск

Публичный VPS читает/получает готовые данные и обслуживает сайт. Он не обязан вызывать облачную модель. Если нет исходящего доступа к GitHub, доверенный исполнитель доставляет проверенный пакет через существующий канал деплоя.

Подлинность пакетов проверяется подписью или серверной аутентификацией, проверкой времени/версии и защитой от повтора. Удалённые медиа проверяются по разрешённым схемам и хостам; произвольный HTML/JS не исполняется. Секреты и личные поля не попадают в публичный пакет.

Для статического сайта: сформировать HTML/JSON, проверить сборку, выложить во временный каталог и атомарно переключить релиз. Для существующего серверного сайта: адаптер обновляет данные с инвалидацией кеша. Команда выбирает вариант после WEB-00, не переписывает сайт только ради импорта.

Откат сайта не должен терять журнал записей и перезаписывать пользовательские данные. Хранить предыдущий успешный релиз и подтверждения доставок. После отката сверить фактическую revision с дашбордом.

## 9. Аналитика и качество

События аналитики: event_list_view, event_detail_view, registration_click, registration_started, registration_confirmed, registration_cancelled, waitlist_joined, check_in, article_view, article_to_event_click, sync_failed, publication_failed.

Клик измеряется на сайте. registration_confirmed и check_in поступают из доверенного регистрационного сервиса. До появления интеграции показывать «данные недоступны», а не оценивать регистрации по кликам. Для группового гостевого формата единицу учёта определить явно.

Полезные измерения: event_id, article_id, revision, category, source/campaign, точка входа. Имена, телефоны, адреса почты и Telegram ID не помещать в URL и общие аналитические события.

Отчёт: просмотры события → переходы к записи → подтверждённые регистрации → визиты. Отдельно доля новых и повтор за 30 дней на зрелых когортах. Сохранять неизвестные источники и согласованное определение атрибуции. Рост охватов не является критерием технической приёмки.

Цели качества новой версии:
- [ ] Ширины 360, 390, 768 и 1440 px без горизонтального скролла и перекрытых кнопок.
- [ ] Полный путь по клавиатуре, видимый focus, корректные заголовки и подписи полей; обычный текст с контрастом минимум 4.5:1.
- [ ] Уважать prefers-reduced-motion, не загружать тяжёлое видео как условие доступа к расписанию.
- [ ] Измерять LCP, INP и CLS на доступных устройствах. Цели: LCP ≤2.5 с, INP ≤200 мс, CLS ≤0.1 на 75-м процентиле полевых данных при наличии выборки [R11]. До накопления данных отдельно приложить лабораторные результаты, не называть их полевыми.
- [ ] Для события создать schema.org Event с данными, совпадающими с видимой страницей, включая перенос/отмену. Не обещать расширенное отображение в поиске [R10].
- [ ] Для статьи добавить Article и BreadcrumbList там, где они соответствуют странице.
- [ ] Проверить title, description, canonical, HTTP 404, redirects, sitemap и robots.
- [ ] Не раскрывать списки участников публично. Контакт, доступ к экспорту и удаление данных должны соответствовать утверждённой политике клуба; тексты не подменять чужими шаблонами без проверки.
- [ ] Для публичных форм предусмотреть ограничение частоты, серверную валидацию и защиту от повторного создания записей.

## 12. Решения и вопросы до выпуска

Уже задано владельцем:
1. Договорённости CMO фиксируются в собственной папке Git.
2. События автоматически поступают из существующей Google-таблицы.
3. Статьи готовятся через существующий отдел Content Factory и Git, доставляются на сайт и отображаются в её дашборде.
4. Нужен пошаговый план для команды, а не замена сайта в этом чате.

Не установлено и требует проверки:
- Репозиторий и рабочая ветка публичного сайта; работающий канал деплоя.
- Смысл текущего статуса «1», подтверждённые поля цены/длительности и правила публикации строк.
- Поддержка event_id, листа ожидания и callback подтверждения существующим ботом.
- Реальное устройство API дашборда и путь импорта статьи.
- Исполнитель LLM по расписанию и его доступы; дни/время генерации и публикации.
- Точные ответственные и их доступное время.

Предлагается принять в первой волне: список событий по умолчанию, атомарный импорт, регистрация через существующий бот, новая страница события. Предлагается второй волной: доставка статей, планировщик, сверка версий и аналитика.

Приоритеты первого аудита от 14.11 остаются рекомендациями до явного подтверждения. Настоящая просьба о ТЗ не считается автоматическим согласием с каждой маркетинговой гипотезой.
