# Как директор работает по расписанию

## Чат и постоянно работающий агент

Этот чат — место диалога с директором. У текущей сессии нет подтверждённого
инструмента, который может будить другие пользовательские чаты или запускать
их по расписанию. Не следует автоматизировать это кликами по интерфейсу чатов.

В актуальной ветке `claude/lucid-bohr-j6mlrh` уже выбран вариант A:
облачный планировщик Claude запускает агентов; VPS хранит витрину и принимает
результаты. Это описано в `shared/automation/README.md` и
`NEXT-SESSION-LAUNCH.md`. Сохраняем это решение, не заменяем его обязательным
новым платным LLM-бэкендом на VPS.

В текущем чате нет инструмента `claude-code-remote` / scheduled tasks.
Следовательно, создать и проверить эти облачные расписания здесь пока нельзя.
Утверждения старых инструкций о доступности подписочного запуска нужно проверить
в том runtime, который фактически подключат: документация проекта не доказывает
возможности или тарифы платформы. Нужен поддерживаемый коннектор/runtime для
создания заданий, запуска агентов и чтения статуса.

Уже реализованные HTTP-точки: `/api/content/ingest`, `/api/scout/ingest`,
`/api/analytics/ingest`; используемые секреты — только через окружение.
Источник URL — `CONTENT_FACTORY_WEB_URL`; целевой веб —
`content.vernatunspeakclub.com`. Факт доступности продакшена не проверен.
Состояние `approved` и фактическая публикация в соцсети различаются.

## Резервный вариант: отдельный runner на VPS

1. Панель директора и общий API: стратегия, календарь, статусы, задания, файлы.
2. PostgreSQL: источник истины для брифов, версий, запусков, результатов и апрувов.
3. Планировщик с timezone `Europe/Moscow`: создаёт задания, не генерирует сам.
4. BullMQ + Redis: очередь, отдельные workers и повтор после временной ошибки.
5. Workers: директор → исследователь → сценарист → дизайнер/монтажёр → редактор.
   Каждый получает свой role prompt, разрешённые инструменты, бренд-бриф и задание.
6. Файловое/S3-совместимое хранилище: медиа и манифест результата.
7. Доска: просмотр файлов, замечания, повтор этапа и явный апрув владельца.
8. Публикатор: отдельный исполнитель только для одобренной версии и площадки.

В проекте уже объявлены BullMQ, ioredis, node-cron, Prisma и инструкции workers.
Наличие зависимостей не означает, что эта схема реализована и запущена.

## Пример первого рабочего сценария (предложение)

Понедельник, 10:00 МСК → директор выбирает три одобренных брифа недели →
отдельная задача на каждый материал → сценарий → производство → редактор →
статус «На согласовании» и ссылки на готовые файлы в доске.

Число материалов, день и время пока не утверждены. До утверждения сценарий не активировать.

Вход задания: `job_id`, `content_id`, `brief_version`, `role`, `input_refs`,
`deadline`, `budget_limit`, `approval_version`.

Выход: `status`, `artifact_refs`, `quality_report`, `cost`, `next_role`, `error`.
Задачи с отсутствующим брифом/ассетами получают «Нужны данные», а не выдуманный результат.

## Обязательные свойства первого запуска

- Уникальный ключ (материал + этап + версия) исключает повтор при рестарте cron.
- Повторы ограничены; повтор публикации сверяет внешний идентификатор результата.
- Лимит бюджета, числа задач и длительности; понятная кнопка остановки.
- Секреты — только в защищённой конфигурации VPS; без значений в логах и заданиях.
- Никакой автоматической публикации или рассылки без соответствующего апрува.
- Апрув относится к версии результата: правка после апрува требует нового.
- Общая память в БД/репозитории: каждый агент читает свою роль, бриф и релевантный контекст.
- Пробный сквозной запуск без публикации, затем тест перезапуска и защиты от дублей.

## Как этот чат будет связан с VPS

Поддерживаемое подключение MCP/API может дать директору инструменты
`list_content`, `create_brief`, `enqueue_pipeline`, `get_job`, `list_artifacts`.
Их ещё нужно реализовать и подключить; они не существуют от записи названий здесь.
Авторизация должна ограничивать проект и разрешённые действия.
Тогда по команде в чате директор отправляет задачу, а VPS исполняет её независимо
от жизни сессии. Расписание хранится на VPS и вызывает ту же очередь напрямую.

Для резервного варианта нужны: утверждённый runtime, модельный
провайдер/API-бюджет, общий storage и первый конкретный пайплайн с форматом результата.
Секретные значения вводятся через настройки сервера, не в переписке.
