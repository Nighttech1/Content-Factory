# Доработка транспорта для разрешённого Apify-сбора

06.11.2026. Владелец повторно подтвердил общий предел исследования $1. Это не новый доллар сверх v4. Сохраняются $0.50 Instagram/$0.50 TikTok, максимум по одному запуску, никакого автоматического перезапуска.

Порядок локальной работы (последовательное исполнение одним агентом, не независимые субагенты): проверка готовности инструкций → спецификация → доработка Python/ручного workflow → офлайн-проверки → фиксация результата. UI/БД/LLM/деплой неприменимы: меняется только транспорт Scout вне веб-продукта. Подключённые методы: scout-actions/scout-apify; инженерный маршрут общей серверной логики — coder. Недостающая оболочка knowledge/engineering/roles/coder.md не заменяется вымышленной инструкцией.

## Конкретная спецификация до кода

- Продолжить существующий `scout-data.yml`, без cron/push/deploy и новых секретов.
- До actor POST прочитать `/users/me/limits` и `/users/me/usage/monthly`; неизвестное/ошибка/параллельный actor/недостаточный остаток → остановка, без actor run. Учитывать меньший из лимита аккаунта и $5; использовать более высокий из двух показателей расхода. Это проверка текущего месячного цикла Apify, не глобальная блокировка чужих процессов аккаунта.
- IG: максимум 7 профилей, свой включён, максимум 6 публикаций на профиль. TikTok: максимум 5, максимум 6; только подтверждённые профили, без артистов и случайных подстановок. Недобор предпочтительнее нерелевантного сбора.
- Перед стартом получить текущую pricingInfos выбранного актора; поддерживать только известные PPE/PPR, не запускать без метаданных тарифа.
- Один POST запуска с `maxTotalChargeUsd <= 0.50`, `restartOnError=false`, timeout=180. Сразу сохранить run ID. Проверять состояние только GET; никаких повторов POST. Сохранить стоимость из run metadata, ошибки/пустая выдача не обнуляют расход.
- Общая последовательная блокировка workflow для Apify; повтор attempt>1 запрещён до actor POST. Директор задаёт выборку; код не запускается от чтения инструкции.
- Секреты только в Authorization; stdout/артефакты без значений ключей. Публичные метрики отделять от закрытых. Сырые данные только артефакт, без публикации.
- Нет установленного счётчика отчёта в аккаунте: оператор перед каждым ручным запуском проверяет журнал, не делает второй запуск той же площадки. Два потолка по $0.50 обеспечивают суммарный предел $1 при соблюдении этого правила. Новые сборы за пределами двух запусков не разрешены.

## Критерии проверки

Офлайн: отсутствие API при запрете/неизвестном остатке, недостаточных средствах, параллельных jobs и повторе attempt; максимум один actor POST; cap и выключенные дополнения; сохранение run ID/стоимости при ошибке; границы размеров выборки, обработка недобора, отсутствие секретов. Локальная проверка не подтверждает реальную валидность токена или остаток.

## Граница внешней записи

В ТЗ v3 прямо сказано: «commit/push этим заданием не разрешены». В v4 снят запрет на существующий workflow и задан расход, но не на изменение удалённого Git. Текущее повторное разрешение $1 не трактуется как снятие этого отдельного запрета. Поэтому до отдельного разрешения подготовленный патч остаётся локальным; удалённые файлы не изменяются, токен не извлекается обходным путём. Разрешение требуется именно на обновление транспорта в GitHub, не повторно на бюджет/API.
