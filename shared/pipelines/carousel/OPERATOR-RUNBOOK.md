# Карусели Вернатуна: порядок работы и контрольные точки

Актуализация по решениям владельца 2026-11-14. Для carousel-чата этот документ уточняет исторические инструкции. Работа ведётся в одном чате последовательными ролями; отдельные субагенты запускаются только при разрешении и фактической доступности. Переключение роли не является независимой проверкой.

## Два входа

1. Прямое поручение владельца: записать его как источник brief; не требовать повторного объяснения директору.
2. Задание директора через веб: сначала подтвердить фактическое получение runtime/коннектором. Запись в Git или вебе сама по себе не запускает чат.

Для нового production сохраняются ID V-ГГГГММ-CAR-NN, папка jobs и версия brief/сценария. Исторический пакет из этого чата не получил директорский ID; сохранённый case-v3.json явно является replay-fixture. Не выдумывать ID или прошлые апрувы.

## Что зафиксировано, а что подбирается

- Персонаж выбирается под задание. Утверждённая Ануш в текущем наборе — с тёмным каре до плеч. Старый длинноволосый sheet не подмешивать. Референсы в существующей Google-папке heros обновлены отдельно.
- Единая техника всех людей и единая основная локация на карусель; разные постановки, действия, масштаб и глубина.
- Type 1: 7 слайдов; на 2–6 по 3 записи, каждая Armenian / Latin transliteration / Russian. Hook/final могут содержать AI-типографику; логотип никогда не генерируется.
- Главный шрифт Noto Serif Display Black 900; Armenian — Noto Sans Armenian. Реальные assets для управляемых строк, без silent fallback. AI-типографика — визуальная имитация, а не доказательство гарнитуры.
- Canvas 1080×1350. **Лого: сверху 54 px, справа 54 px**, ширина текущего набора 160 px. Это явное исключение из прежних 7–8% только для логотипа; text-safe zone не отменяется. Размер/пропорции логотипа не менять при изменении отступов.
- Логотип — утверждённый dark/light asset, без перерисовки, подложки, тени и нового wordmark.
- Стрелка на 1–6, на финале отсутствует. Основной цвет только black/white по локальному контрасту; тонкий противоположный контур для фактурного фона. Никакого оранжевого по умолчанию. Числовая эвристика не заменяет мобильный просмотр.
- Цвет, прозрачность, координаты и размеры карточек задаёт арт-директор в job JSON. Не переносить цвет демонстрационного набора молча в каждую новую карусель. Один блок = одна компактная плашка, без вложенных подложек.

## Кодовая последовательность шага 4

Исполняемые инструменты: [bake/README.md](bake/README.md). Не писать новый рендерер при каждой сессии.

1. Проверить input contract: accepted backgrounds, hashes всех ассетов, строки и число фраз, координаты, шрифты, version.
2. Отделить generation от bake: брать только принятые фоны. Любой RETURN/REGENERATE блокирует следующий этап.
3. Подготовить точный HTML/CSS/SVG, assets и 40-bake-manifest с фактическими размерами строк и всех слоёв.
4. Канонический экспорт — Chromium. Дождаться реальной загрузки шрифтов и изображений, проверить DOM bounds, количество строк/стрелок, отступы логотипа и 1080×1350.
5. Если Chromium заблокирован — статус BLOCKED_OR_FAILED. Cairo/Pango разрешён **только как явно обозначенный предпросмотр/воспроизведение**; он не закрывает canonical gate.
6. Проверить отдельные PNG, порядок и contact sheet. Исправление → тот же затронутый прогон проверок. Не выдавать контактный лист за проверку каждого кадра.
7. Повторить сборку из отдельной копии входов; сравнить хеши. Сравнивать один и тот же renderer, fonts и версии среды. Между разными рендерерами/ОС побайтное равенство не обещать.

## Шаг 5: что именно принимает арт-директор и редактор

Вход: композиты, 40-bake-manifest, технический отчёт canonical-report, script/brief и contact sheet. Резервный preview можно обсуждать, но не объявлять production-ready.

Арт-директор смотрит каждый слайд в полном размере и при ширине 360 px, затем весь набор:

- соответствие сценарию, идентичность персонажа и каре, лица, кисти и смысловой eye-line;
- нет повторяющихся постановок или скачков стиля/локации;
- текст не закрывает лицо, руки, действие; нет клиппинга/случайных переносов/лишнего воздуха;
- число фраз, иерархия, читаемость транслитерации/перевода, точный логотип, 54/54, контраст каждого wordmark и каждой стрелки;
- крупные hook/CTA, одна понятная цель действия, отсутствие старого CTA после смены цели;
- фактическая читаемость на телефоне: даже прошедшие формальные размеры возвращаются, если текст плохо читается.

Редактор отдельно проверяет естественность восточноармянских фраз, пунктуацию, единообразную транслитерацию, смысл русского перевода, тон бренда, обещание hook и пользу до CTA. Наличие глифов не доказывает правильность языка.

Выходы: 50-art-qa.md (ACCEPT / RETURN с тикетами), 60-editor-verdict.md (✅ / ❌), внутренняя дизайн-приёмка CLIENT_DESIGN_ACCEPTED только после просмотра всех кадров и закрытия дефектов. Для каждого возврата: slide ID, дефект, ответственный этап, точное исправление, доказательство повторной проверки. См. [шаблон](50-art-qa-TEMPLATE.md).

Технический PASS, визуальный ACCEPT, редакторский ✅, согласие владельца и публикация — разные состояния. Ни один скрипт не предоставляет owner approval и не отправляет материалы в соцсети/веб/Drive. Внешние записи требуют соответствующей команды и доступного транспорта.

## Честное состояние текущего примера

Портированный preview воспроизводит набор v3; нынешняя среда блокирует Chromium. Предыдущий контроль пропустил цвет стрелки — этот класс дефектов теперь имеет кодовый guard и отдельный пункт мобильной приёмки. Проверка шрифтов выявила расхождение actual SHA256 primary с vernatun-fonts.json; оригинальный font asset не менялся. До production явно разрешить расхождение, не подменять файл и не заявлять, что весь контракт шрифтов уже согласован.
