# Архитектура: агенты Клода ↔ веб на российском VPS (ревью/апрув статей)

## Проблема
- **Продюсер:** агенты Клода (облачные сессии) генерят статью.
- **Потребитель:** веб-платформа на **российском VPS** — там владелец смотрит статью (красиво, как Telegra.ph), апрувит или пишет замечания → назад агенту на доработку.
- Прямой коннект агент→VPS нежелателен: хрупко/геозависимо, VPS пришлось бы открывать наружу.

## Решение: нейтральный «облачный ящик» (drop) + VPS ТЯНЕТ сам
Развязываем producer и consumer через **нейтральное хранилище, доступное обеим сторонам** (S3/R2-совместимое, глобально доступно — напр. **Cloudflare R2**: достаётся и из облака Клода, и с российского VPS по HTTPS). Агенты только **пишут** в ящик; VPS только **тянет** (исходящие запросы — работают из РФ к Cloudflare). Никто не «стучится» на VPS.

```
Агент Клода (облако)                 Нейтральный ящик (R2/S3)              Веб на VPS (РФ)
───────────────────                  ─────────────────────                ────────────────
1. собрал статью (блоки) + картинки → articles/<id>/article.json (+img)
                                     ← 2. VPS ПОЛЛИТ ящик (pull) → в БД
                                                                          3. /articles: превью (как Telegra.ph)
                                                                             владелец: Approve / Замечания
                                     articles/<id>/verdict.json ←──────── 4. VPS пишет вердикт+замечания в ящик
5. агент поллит ящик → читает вердикт
   - замечания → дорабатывает → новая версия article.json → (цикл 2–4)
   - approve → Публикатор публикует (Telegra.ph / сайт / Дзен) из одобренной версии
```

**Почему так:**
- Агенты не нуждаются во входящем доступе к VPS; VPS — только исходящие (pull). Нет «Клод → .ru» прямого коннекта.
- Нейтральный ящик достаётся с обеих сторон (Cloudflare R2 глобально доступен и из РФ).
- Устойчиво: VPS офлайн — статьи копятся в ящике; поднялся — забрал.
- Картинки — в ящик (не в git), git остаётся крошечным (только текст, если нужен).

## Превью в вебе = как в Telegra.ph (один источник)
Статья хранится как **упорядоченные блоки** (h/p/img/video). И веб, и Telegra.ph рендерят из ОДНОГО источника → картинки внутри текста, одинаково красиво. В разделе `/articles` веба — та же читалка + кнопки **Approve / Замечания**.

## Контракт данных (в ящике)
- `articles/<id>/article.json` — `{ id, version, title, blocks:[...], images:[{id,url,alt}], meta, status }`. Пишет агент.
- `articles/<id>/images/*` — картинки (или прямые R2-URL в blocks). Пишет агент.
- `articles/<id>/verdict.json` — `{ status: approved|changes_requested, comments:[{block_id, text}], by, at }`. Пишет веб (VPS).
- Версионирование: новая доработка → `version++`, новый `article.json`; история ревью в `verdict.json`.

## Петля HITL (замечания → доработка)
`агент → article.json(v1) → веб-превью → замечания(verdict) → агент читает → article.json(v2) → … → approved → публикация.`
Гейт сохраняется: публикуется только `approved`.

## Варианты (если не хочешь отдельный ящик)
- **A (рекоменд.):** R2/S3 как ящик (чисто, устойчиво, геонезависимо). Текст можно дублировать в git, картинки — только в R2.
- **B:** git (GitHub) как ящик для ТЕКСТА (агенты уже пушат туда) + R2 для картинок; VPS делает `git pull` + тянет картинки. Минус: GitHub из РФ бывает нестабилен.
- **C (проще, менее устойчиво):** прямой агент→VPS HTTPS POST + VPS→агент через polling. Работает, если окружение агента разрешает `.ru` и VPS публичный. Для MVP ок, но хуже по устойчивости.

## ⚠️ Ключевой факт: Claude/Anthropic НЕ доступен с российских IP
Anthropic официально не поддерживает доступ из РФ — запрос с **российского IP** к `api.anthropic.com` (и к claude-code-remote) **скорее всего заблокирован**. Это не зависит от того, где физически ты: важен IP **сервера**. Значит:
- **Веб на российском VPS НЕ может звонить Claude напрямую** (даже если ты сам в США — наружу к Claude идёт российский сервер).
- Поэтому «мозг» (агенты) живёт на инфраструктуре Claude (вне РФ), а российский VPS общается с ним **только через нейтрального проводника** (R2/ящик + облачная сессия Claude, которая его слушает). Проводник тут — не лишнее звено, а то, что вообще делает связь возможной.

### Варианты хостинга control-панели (выбор владельца)
- **Вариант 1 (чистый, рекомендую): control-панель на НЕЙТРАЛЬНОМ сервере** (не РФ) — тогда она звонит Claude и R2 **напрямую**, чат с агентами работает прямо в вебе, проводник для чата не нужен. **Публичный сайт `vernatunspeakclub.com` остаётся на российском хостинге** (ему Claude не нужен). Разделяем: сайт — РФ, пульт — нейтральный.
- **Вариант 2: всё на российском VPS + проводник.** Пульт на РФ → чат с агентами идёт асинхронно через R2 (ты пишешь → в ящик → облачная сессия Claude отвечает → в ящик → пульт показывает). Работает, но сложнее и с задержкой.
- **Вариант 3 (проще всего): чат с агентами — прямо в claude.ai / приложении Claude** (глобально, на подписке, из любой точки, включая США). Российский VPS-пульт = только доски/аналитика/апрув (синк через R2). Минус: чат не внутри твоего веба.

> «Без проводника» напрямую с российского VPS к Claude — не выйдет (гео-блок). Без проводника можно только: (а) общаться в claude.ai напрямую (Вариант 3), или (б) держать пульт на нейтральном хостинге (Вариант 1).

### Вариант 4 (решение владельца 2026-10-31): прямой push, вся интеракция в Cloud — БЕЗ ящика
Ключевой инсайт: гео-блок бьёт только по направлению **РФ-IP → Claude**. Поток **Claude-агент (облако) → РФ-VPS** — это обычный исходящий HTTPS-POST из нашего облачного контейнера, под гео-блок Anthropic **не попадает**. Поэтому если:
- вся интеракция (чат/апрув/правки) идёт в **облачном приложении Claude**, а
- VPS-дашборд — **односторонняя витрина** (доски/аналитика), и назад к Claude **ничего не звонит**,
то агенты пишут **прямо на VPS**, и нейтральный R2-ящик **не нужен**.

```
Cloud (вне РФ)                                  РФ-VPS (публичный)
ты ↔ агенты (чат, апрув, правки)  ← всё тут
   [триггер по расписанию будит агента]
   агент собрал контент ──── HTTPS POST (+INGEST_SECRET) ───► /api/ingest → ячейка дашборда
   назад к Claude — НИЧЕГО (нет РФ→Claude запроса)
```

**Условия (не опускать):**
1. **Сеть окружения:** домен VPS добавить в Network access → Allowed domains (меню облачного окружения → Edit). Иначе POST на `.ru` не уйдёт. Разово.
2. **Секрет:** `/api/ingest` принимает запись только с `INGEST_SECRET` (публичный ≠ без пароля). Эндпоинты и секрет — в `shared/automation/README.md`.
3. **Надёжность:** прямой push на один VPS хрупче буфера — агент делает ретраи + идемпотентность (повторный POST того же `id` не плодит дубли). Медиа VPS хостит у себя (в git — только текст).

**Когда всё же нужен ящик/мини-проводник:** как только обратная петля (кнопка «Замечания» на VPS → агенту) должна лететь РФ→Claude — только этот шаг упирается в блок. Тогда либо мини-ящик для вердиктов (Вариант 2), либо владелец даёт правку в облачном чате. Пока интеракция в Cloud — не требуется.

### Сколько стоит ящик (Cloudflare R2) при наших объёмах
- **Хранение:** ~$0.015/ГБ-мес. **Egress (скачивание) — $0 (бесплатно)** — ключевой плюс: VPS тянет данные без платы за трафик.
- **Операции:** запись ~$4.5/млн, чтение ~$0.36/млн.
- **Free-тариф:** 10 ГБ хранения + 1 млн записей + 10 млн чтений — бесплатно.
- **Наши объёмы (с ротацией, без вечного архива):** текст/JSON — килобайты; картинки каруселей ~0.5–2 ГБ/мес; рилсы (видео) — десятки-сотни МБ (сырьё лучше в Google Drive, он подключён). Итого — **в пределах бесплатного или пара $ в месяц.** Ориентир, сверь актуальные цены.
- **Аналоги:** Backblaze B2 (дешевле хранение, egress ~бесплатно до лимита), Wasabi (флэт ~$7/ТБ, без egress), AWS S3 (дороже egress). Для нас R2 оптимален (0 egress + глобально доступен из РФ). Хакерский бесплатный вариант для мелочи — приватный Telegram-канал как «ящик» (бот пишет, VPS читает через Bot API; лимиты на размер файла).

## Что нужно (владелец), минимум для варианта A

- На VPS — поллер (cron): тянет новые `article.json` → в БД; пишет `verdict.json` при апруве/замечаниях.
- В вебе — экран `/articles`: рендер блоков (как Telegra.ph) + Approve/Замечания (команда разработки).
