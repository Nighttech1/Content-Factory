# approve-loop.md — петля апрува в чате + деплой на веб (общее правило)

> Как готовая единица проходит апрув человека ПРЯМО В ЧАТЕ и только потом попадает
> на веб-дашборд как «опубликовано». Дополняет `pipeline-gate.md` (гейты) и
> `agent-roster.md` (кто куда). Действует для всех форматов.

## Поток (по расписанию → апрув в чате → деплой)
```
1. Триггер по расписанию будит лид-агента (см. shared/automation/README.md).
2. Отдел собирает единицу (сценарий → визуал → сборка) → Редактор ✅.
3. Агент САМ приносит готовое владельцу В ЧАТ (даже если владелец спит — лежит в чате к подъёму):
   • превью (слайды/видео/статья-блоки) + краткий питч (что это, куда ведёт в воронку);
   • две кнопки словами:  [✅ Approve]   [✍️ Что поправить].
4. Владелец отвечает:
   • «Что поправить: …» → агент дорабатывает → снова в чат (пункт 3). Цикл сколько нужно.
   • «Approve» → переход к пункту 5.
5. ТОЛЬКО после Approve агент деплоит единицу на веб-дашборд как «опубликовано»:
   POST {CONTENT_FACTORY_WEB_URL}/api/content/ingest  (заголовок x-ingest-secret: INGEST_SECRET)
6. Публикация в соцсети — ПОКА ВРУЧНУЮ: агент отдаёт владельцу готовые слайды/видео/текст,
   владелец сам выкладывает в Instagram и др. (авто-Публикатор — Фаза P, позже).
```

## Жёсткие правила
- **Без Редактора ✅ — не показывать владельцу.** Без Approve владельца — **не** деплоить на веб и **не** отдавать на публикацию. Два гейта подряд (Редактор, затем человек) — закон.
- **Approve в чате = разрешение только на «положить на веб как опубликовано»** (витрина) и отдать владельцу файлы. Это НЕ авто-постинг в соцсети.
- **Деплой идемпотентен:** один и тот же `id` перезаписывает карточку на дашборде, не плодит дубли (безопасно для ретраев, если VPS временно недоступен — повторить с тем же `id`).
- **Медиа — ссылками.** В `assets` — URL (хостит площадка/VPS/хранилище), не файлы. git остаётся текстовым.
- **Роль-метка всегда.** Принёс в чат, дорабатываю, деплою — помечай роль (🎨/🎬/✍️) и статус.

## Контракт пуша на веб (`POST /api/content/ingest`)
```json
{
  "id": "V-202611-18",                      // стабильный id (для идемпотентности); можно = unitId
  "unitId": "V-202611-18",                  // ID из контент-плана
  "type": "carousel",                        // carousel | reel | article | youtube | post
  "title": "5 мест для армянина в Москве",
  "status": "published",                     // approved | published
  "assets": [                                 // ссылки, не файлы
    { "kind": "cover",  "url": "https://.../cover.jpg", "alt": "обложка" },
    { "kind": "slide",  "url": "https://.../s2.jpg" }
  ],
  "blocks": [ /* для статей: упорядоченные h/p/img/video, как Telegra.ph */ ],
  "channels": ["instagram", "telegram"],     // куда владелец выложит/выложил
  "source": "scriptwriter-carousel",          // кто прислал
  "meta": { "approvedBy": "owner", "note": "правки учтены v2" }
}
```
Авторизация: `x-ingest-secret: <INGEST_SECRET>` (или `Authorization: Bearer <INGEST_SECRET>`).
База — `CONTENT_FACTORY_WEB_URL` из окружения. Ответ: `{ ok, id, status, count }`.

## Что нужно, чтобы деплой заработал вживую (владелец/окружение)
1. Веб развёрнут на VPS, у него есть `/api/content/ingest` (готов в `веб/`).
2. В окружении агентов: `CONTENT_FACTORY_WEB_URL` (адрес веба) + `INGEST_SECRET` (общий секрет).
3. В настройках облачного окружения: домен VPS добавлен в **Network access → Allowed domains**
   (иначе исходящий POST на `.ru`-хост не уйдёт). Разовая настройка владельца.
> До развёртывания: агент складывает одобренное в `drafts/ГГГГ-ММ/` и отдаёт владельцу файлы;
> деплой на веб включается, как только адрес+секрет+сеть готовы.
